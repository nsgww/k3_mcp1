# 组播音频输入使用说明

k3_mcp1 语音助手（`09_asr_llm_ws.py`）支持从 UDP 组播获取音频，与 multi-stream-asr 语音转写的 `/ws/multicast` 同一协议、同一风格。音频改从组播进来后，后续流程（唤醒门控 KWS+VAD → ASR → LLM/MCP → TTS 播报）与麦克风模式完全一致，识别结果和语音照常通过 WebSocket 下发给客户端。

## 接口地址

| 路径 | 输入源 |
|---|---|
| `ws://<板子IP>:8060/stream` | 客户端麦克风 PCM 上行（原有） |
| `ws://<板子IP>:8060/stream/multicast` | 组播音频输入 |

连接参数（可选）：

```
ws://192.168.1.140:8060/stream/multicast?group=224.2.1.209&port=6020
```

- `group`：组播地址，默认取环境变量 `MCAST_GROUP`，缺省 `224.2.1.209`
- `port`：组播端口，默认取环境变量 `MCAST_PORT`，缺省 `6020`

## 前端（lg-store）经 nginx 接入

浏览器前端不走 8060 直连，而是经 nginx 入口（HTTPS 8443，麦克风安全上下文要求）：

| 前端 WebSocket 地址 | 实际到达 | 模式 |
|---|---|---|
| `wss://<板子IP>:8443/ws/asr-llm` | `:8060/stream` | 客户端麦克风上行 |
| `wss://<板子IP>:8443/ws/asr-llm/multicast?group=224.2.1.209&port=6020` | `:8060/stream/multicast` | 组播输入 |

注意：

- **`/ws/asr-llm` 会被 nginx rewrite 成 `/stream` 且丢弃 query**——组播必须用 `/ws/asr-llm/multicast` 这个更长的路径，query 里的 `group`/`port` 会保留透传
- 80 端口（HTTP）同样可用：`ws://<板子IP>/ws/asr-llm/multicast?...`
- 局域网内不开页面也可直连 `ws://<板子IP>:8060/stream/multicast`

## 消息交互

连接后服务端先下发 hello：

```json
{"type": "status", "message": "connected, ...", "source": "multicast 224.2.1.209:6020",
 "kws_enabled": true, "tts_enabled": true, "wake_gate": true, "mcp_tools": [...]}
```

之后流程与麦克风模式相同：

1. 对音源说唤醒词（如「小朗小朗」）→ 收到 `{"type":"kws","keyword":"小朗小朗"}` + `{"type":"wake_state","state":"woken"}` + 应答 TTS
2. 说指令 → 收到 `asr`（识别文本）→ `llm`（回复）→ TTS 音频（二进制 wav 帧）
3. 一轮结束后回 IDLE，等待下次唤醒

组播模式下客户端**无需发送音频**（上行二进制会被忽略）；JSON 控制消息（`ping`、`wake_gate`、`kws_keywords` 等）照常可用。

> 常见坑：连成了 `/stream`（或经 nginx 的 `/ws/asr-llm`）却按组播用法不发音音频——那是麦克风模式，门控收不到任何声音，表现为"能连上但说话没反应"。先确认 hello 里的 `source` 字段是 `multicast ...` 还是 `ws`。

### 切换组播地址

```json
{"type": "set_multicast_group", "group": "224.2.1.213", "port": 6032}
```

服务端重新加入新组并回确认：

```json
{"type": "status", "message": "multicast group=224.2.1.213:6032", "source": "multicast 224.2.1.213:6032"}
```

`group`/`port` 可只给一个，另一个保持当前值。
